# static-verification Specification


## Purpose

Зафиксировать семантику статической проверки bigint- и number-контрактов, условия получения доказательств и контрпримеров, а также сохранение неопределённости и общего результата программы.

## Requirements

### Requirement: Точная целочисленная арифметика

Верификатор SHALL проверять поддерживаемые bigint-операции в модели bigint-exact-integers с целыми произвольной величины. Сложение, вычитание, умножение, унарный минус и сравнения SHALL сохранять целочисленную семантику без округления и переполнения фиксированного разряда. Статическая проверка SHALL NOT исполнять пользовательский код.

#### Scenario: Дискретность целых

- **WHEN** requires задаёт x > 0n, а ensures требует result >= 1n для функции identity
- **THEN** постусловие доказывается

#### Scenario: Отсутствие фиксированного предела

- **WHEN** функция возвращает x + 1n, а ensures требует result > x при любом bigint x
- **THEN** постусловие доказывается без ограничения разрядности

#### Scenario: Произведение произвольной величины

- **WHEN** функция возвращает x * y для bigint, в том числе значений за пределами safe integer
- **THEN** произведение сохраняет каждый разряд и знак без преобразования в number

#### Scenario: Нелинейные условия

- **WHEN** функция возвращает x * x с ensures: r => r >= 0n
- **THEN** постусловие доказывается для любого bigint

#### Scenario: Ограниченные ресурсы умножения

- **WHEN** solver исчерпывает лимит ресурсов на условии с умножением
- **THEN** результат остаётся unknown/solver-unknown с причиной, без ложного proved или counterexample

### Requirement: Совместимость предусловий

Верификатор SHALL отдельно проверять существование входов, удовлетворяющих requires. Совместимые предусловия SHALL давать satisfiable; противоречивые — inconsistent; отсутствие ответа solver — unknown. При inconsistent или unknown для предусловий верификатор SHALL NOT выдавать доказательство реализации этой функции.

#### Scenario: Пустой целочисленный интервал

- **WHEN** requires задаёт 0n < x && x < 1n
- **THEN** результат совместимости равен inconsistent, а успешное доказательство реализации отсутствует

#### Scenario: Неполученная совместимость

- **WHEN** solver исчерпывает лимит ресурсов при проверке requires
- **THEN** совместимость остаётся unknown с причиной solver, без vacuous proved для реализации

#### Scenario: Нет requires

- **WHEN** контракт содержит только ensures
- **THEN** отсутствует отдельный результат preconditions, а входы не ограничены неявным предусловием

#### Scenario: Requires без callers

- **WHEN** requires-only функция не имеет мест вызова в графе
- **THEN** проверяется совместимость requires; это не считается доказательством соблюдения requires внешними callers

### Requirement: Проверка постусловия реализации

Для функции с совместимыми предусловиями верификатор SHALL проверять ensures для результата её тела на допустимых входах. Отсутствие нарушающей модели SHALL давать proved. Нарушающая модель без абстрактных результатов вызовов и с полным конкретным поддерживаемым входом SHALL давать disproved с точными входными аргументами и причиной contract-violation.

#### Scenario: Правильное снятие средств

- **WHEN** withdraw возвращает balance - amount и контракт требует достаточного баланса и соответствующего неотрицательного остатка
- **THEN** постусловие реализации получает proved

#### Scenario: Ошибочная реализация

- **WHEN** та же реализация возвращает balance + amount
- **THEN** верификатор возвращает disproved и аргументы, нарушающие ensures при выполненном requires

#### Scenario: Только ensures

- **WHEN** number identity имеет только ensures: (r, x) => r === x
- **THEN** проверка включает все number-входы и находит NaN-контрпример

#### Scenario: Нет ensures

- **WHEN** контракт содержит только requires
- **THEN** implementation-обязательство не создаётся

### Requirement: Проверка предусловий вызова

Верификатор SHALL проверять requires вызываемой функции с подставленными аргументами, учитывая requires вызывающей функции и условия конкретного пути. Вызовы внутри функции без собственного контракта SHALL также проверяться. Один исходный вызов на разных путях SHALL проверяться отдельно для каждого пути.

#### Scenario: Полный и неполный guard

- **WHEN** один caller исключает amount > balance перед withdraw, а другой не исключает
- **THEN** безопасный вызов получает proved, а небезопасный — disproved с аргументами caller

#### Scenario: Caller без контракта

- **WHEN** функция без собственного контракта вызывает функцию с requires
- **THEN** предусловие вызова проверяется с условиями её пути без добавления собственного requires

#### Scenario: Общий вызов на двух путях

- **WHEN** один исходный вызов достигается по двум путям и только один допускает недопустимые аргументы
- **THEN** результаты сохраняют proved для безопасного пути и disproved для нарушающего пути

#### Scenario: Нет requires у callee

- **WHEN** callee имеет только ensures
- **THEN** для этого вызова не создаётся обязательство call, но его заданное ensures проверяется по реализации

### Requirement: Модульное использование контрактов вызываемых функций

Верификатор SHALL проверять заданное requires вызова до использования заданного ensures на соответствующем пути. Без requires входы не ограничены; без ensures результат callee не имеет гарантии. Абстрактный числовой результат SHALL сохранять происхождение независимо от наличия ensures. Заданные ensures callee SHALL проверяться отдельно; ошибка или unknown SHALL препятствовать общему verified.

#### Scenario: Передача гарантии caller

- **WHEN** контракт callee гарантирует result === x, а caller возвращает callee(x) с тем же постусловием
- **THEN** гарантия callee используется для доказательства caller

#### Scenario: Ошибка внутри callee

- **WHEN** caller соответствует контракту callee, но реализация callee нарушает собственный ensures
- **THEN** общий результат не равен verified и содержит нарушение реализации callee

#### Scenario: Requires-only callee

- **WHEN** доказательство caller зависит от результата callee без ensures
- **THEN** результат не получает выдуманного ограничения; нарушающая абстрактная модель даёт unknown/weak-callee-contract без counterexample

### Requirement: Неопределённость при абстрактных результатах вызовов

Если нарушающая модель постусловия реализации получена при использовании абстрактных результатов callee, верификатор SHALL возвращать unknown с причиной weak-callee-contract без конкретного контрпримера. Такой результат SHALL NOT объявляться подтверждённой ошибкой исполнения.

#### Scenario: Недостаточное ensures

- **WHEN** identity гарантирует только result >= 0n, а caller требует result === x
- **THEN** недоказанное постусловие caller получает unknown/weak-callee-contract без counterexample

#### Scenario: Усиленный контракт

- **WHEN** ensures identity усилен до result === x и остальные обязательства корректны
- **THEN** постусловие caller может быть доказано с использованием этой гарантии

### Requirement: Лимиты solver и сохранение unknown

Каждый запрос solver SHALL по умолчанию иметь тайм-аут 5000 мс. Программные timeoutMs и resourceLimit SHALL принимать только положительные целые значения до 2147483647. При отсутствии ответа solver верификатор SHALL сохранять unknown/solver-unknown и исходную причину как для совместимости предусловий, так и для доказательств.

#### Scenario: Исчерпание ресурсов

- **WHEN** resourceLimit: 1 приводит к исчерпанию ресурсов на существующем тестовом корпусе
- **THEN** неполученные результаты сохраняются как unknown с причиной solver и не становятся proved

#### Scenario: Некорректный лимит

- **WHEN** timeoutMs или resourceLimit равен нулю, отрицательному, дробному или слишком большому значению
- **THEN** программный вызов отклоняет лимит

### Requirement: Общий статус проверяемого графа

Верификатор SHALL вычислять общий статус из всех результатов с приоритетом inconsistent, затем refuted при наличии disproved, затем unknown, затем verified. Локальный proved SHALL NOT считаться подтверждением всего графа при наличии других неуспешных результатов.

#### Scenario: Правильная реализация и небезопасный caller

- **WHEN** реализация withdraw имеет proved, но один её вызов имеет disproved
- **THEN** общий статус равен refuted

#### Scenario: Противоречивый контракт в графе

- **WHEN** хотя бы один контракт имеет inconsistent при наличии других результатов
- **THEN** общий статус равен inconsistent, а отдельные результаты сохраняются для диагностики

#### Scenario: Локальная неопределённость

- **WHEN** одно указанное условие имеет unsupported-dependency, а другое доказано
- **THEN** оба результата сохраняются; при отсутствии inconsistent/disproved общий статус unknown

### Requirement: Отказ от неподдерживаемой числовой модели

Для неподдерживаемого сочетания числовых моделей программная проверка SHALL возвращать unknown с semantics unsupported и reasonCode unsupported-numeric-model. Поддерживаемый однородный number-граф SHALL проверяться в модели number-ieee754-binary64. Верификатор SHALL NOT подменять number вещественной арифметикой или выдавать proved для неподдерживаемой модели.

#### Scenario: Дробная арифметика JavaScript

- **WHEN** контракт функции над number описывает сложение 0.1 и 0.2 с ожидаемым результатом 0.3
- **THEN** для функции без параметров, возвращающей 0.1 + 0.2 при requires: () => true и ensures: result => result === 0.3, отчёт имеет refuted и disproved реализации

#### Scenario: Смешанный граф

- **WHEN** проверяемые зависимости корректно типизированного достижимого графа требуют bigint- и number-моделей
- **THEN** отчёт имеет unknown, semantics unsupported, unsupported-numeric-model и пустой список results

### Requirement: Точная binary64 арифметика

Верификатор SHALL проверять number-сложение, вычитание, умножение, деление и унарный минус по JavaScript binary64, включая round-to-nearest ties-to-even, subnormal, переполнение, NaN, бесконечности и знаковый ноль. Область входов SHALL включать все number-значения без неявных ограничений конечности. Статическая проверка SHALL NOT исполнять пользовательский код.

#### Scenario: Потеря точности целого

- **WHEN** функция возвращает x + 1, requires задаёт x === 9007199254740992, а ensures требует result > x
- **THEN** реализация получает disproved с воспроизводимым входом 9007199254740992

#### Scenario: Переполнение и неопределённая разность

- **WHEN** проверяются сложение двух максимальных конечных number и вычитание Infinity - Infinity
- **THEN** результаты модели совпадают с JavaScript: Infinity и NaN соответственно

#### Scenario: Subnormal и знаки нуля

- **WHEN** проверяются 5e-324 + 5e-324, 5e-324 - 5e-324, -(-0) и -0 + -0
- **THEN** модель сохраняет соответственно 1e-323, +0, +0 и -0 без потери subnormal или знака нуля

#### Scenario: Граничные произведения binary64

- **WHEN** проверяются 0.1 * 0.2, 1e308 * 2, 0 * Infinity, -0 * -1 и 5e-324 * 0.5
- **THEN** модель совпадает с JavaScript, сохраняя округление, Infinity, NaN и соответствующий знак нуля

#### Scenario: Неверная гарантия произведения

- **WHEN** функция возвращает x * 0 с ensures: r => r === 0 без ограничения входов
- **THEN** реализация получает disproved с воспроизводимым NaN или бесконечным входом

#### Scenario: Граничные частные binary64

- **WHEN** проверяются 1 / 3, 1 / -0, 0 / 0, Infinity / Infinity, 1 / Infinity, 5e-324 / 2 и 1e308 / 0.5
- **THEN** модель совпадает с JavaScript, включая округление, знаки нуля и бесконечности, NaN, subnormal и переполнение

### Requirement: Number-сравнения и строгое равенство

Number-сравнения и строгие равенства SHALL совпадать с JavaScript: все упорядоченные сравнения с NaN ложны, NaN === NaN ложно, NaN !== NaN истинно, +0 === -0 истинно. Эти правила SHALL применяться и в предикатах, и в условиях ветвей без алгебраических замен, меняющих их смысл.

#### Scenario: Identity на NaN

- **WHEN** identity возвращает x с requires: () => true и ensures: (result, x) => result === x
- **THEN** проверка реализации находит NaN-контрпример

#### Scenario: Неэквивалентные сравнения

- **WHEN** при x равном NaN проверяются x <= 0 и !(x > 0)
- **THEN** первая формула ложна, а вторая истинна

#### Scenario: Знаки нуля в равенстве

- **WHEN** предусловие ограничивает x === 0, а постусловие требует result === -0 у identity
- **THEN** постусловие доказано для обоих знаков входного нуля

### Requirement: Number-обязательства и условия путей

Совместимость requires, проверка реализации, внутренних вызовов и общего статуса SHALL применяться к number с прежними правилами, лимитами и диагностическими причинами. Вызовы на разных путях SHALL сохраняться отдельно. Абстрактная нарушающая модель из слабого callee-контракта SHALL оставаться unknown без конкретного контрпримера.

#### Scenario: Противоречивое number-предусловие

- **WHEN** requires требует x < 0 && x >= 0
- **THEN** совместимость имеет inconsistent, а доказательство реализации не выдаётся

#### Scenario: NaN обходит отрицательный guard

- **WHEN** caller без контракта возвращает 0 при x < 0, иначе вызывает callee с requires: x => x >= 0
- **THEN** проверка вызова находит NaN-контрпример на пути к callee

#### Scenario: Общий number-вызов на разных путях

- **WHEN** общий return после вложенных if достигается по безопасному и нарушающему предусловие callee путям
- **THEN** результаты сохраняют один callId, разные pathCondition и соответствующие статусы

#### Scenario: Слабый number-контракт callee

- **WHEN** callee возвращает x, гарантирует только result >= 0 при конечном неотрицательном x, а caller требует result === x
- **THEN** недоказанное постусловие caller имеет unknown/weak-callee-contract без counterexample

#### Scenario: Ошибка number-callee в графе

- **WHEN** caller соответствует контракту callee, но реализация callee нарушает собственный ensures
- **THEN** общий статус не равен verified даже при локальном proved caller

#### Scenario: Ресурсы binary64 solver исчерпаны

- **WHEN** solver не получает ответ при заданном лимите ресурсов на проверке requires или обязательства
- **THEN** результат имеет unknown/solver-unknown с причиной; ни отсутствие модели, ни лимит не превращаются в proved

### Requirement: Неподдерживаемые зависимости условия

Если условие, его предусловия или необходимые условия пути зависят от неподдерживаемого значения или операции, верификатор SHALL вернуть unknown/unsupported-dependency для затронутого обязательства. Он SHALL NOT игнорировать такое предусловие, подменять значение числом или выдавать proved на основании неполной формулы.

#### Scenario: Неподдерживаемое requires

- **WHEN** ensures числовой, но requires использует свойство объекта
- **THEN** совместимость и зависящее доказательство остаются unknown; requires не заменяется на true

#### Scenario: Независимое условие

- **WHEN** неиспользуемая строка присутствует в сигнатуре identity(x: number, label: string), requires задаёт x >= 0, ensures задаёт r >= 0
- **THEN** условия проверяются в number-модели без ограничений на label

### Requirement: Полнота входа нарушающей модели

Верификатор SHALL выдавать disproved только с полным конкретным поддерживаемым входом исходной функции и поддерживаемым путём. Если точная формула имеет нарушающую модель, но непрозрачные аргументы не позволяют получить полный вход, результат SHALL быть unknown/incomplete-counterexample без counterexample. Отсутствие нарушающей модели в точной проекции SHALL допускать proved.

#### Scenario: Не задан объект для воспроизведения

- **WHEN** нарушающая модель найдена для числового условия функции с непрозрачным объектным параметром
- **THEN** результат unknown/incomplete-counterexample; объект не заменяется на {} или undefined

#### Scenario: Неиспользуемый числовой параметр

- **WHEN** нарушение найдено у полностью числовой функции с неиспользуемым параметром
- **THEN** counterexample содержит все исходные числовые аргументы в точной кодировке

### Requirement: Семантика строк UTF-16

Верификатор SHALL моделировать строки как последовательности кодовых единиц UTF-16, сохраняя пустую строку, NUL и одиночные суррогаты. Равенство SHALL сравнивать всю последовательность, + SHALL соединять строки, .length SHALL возвращать число кодовых единиц с number-семантикой. Проверка SHALL относиться к нормальному завершению; ограничения памяти конкретного движка не доказываются.

#### Scenario: Emoji и суррогаты
- **WHEN** проверяются длины "😀", "\ud800" и "\u0000"
- **THEN** получаются соответственно 2, 1 и 1; surrogate pair равен соответствующему emoji

#### Scenario: Конкатенация и равенство
- **WHEN** функция возвращает a + b, а ensures требует result === a + b
- **THEN** постусловие доказано; перестановка a и b допускает конкретный контрпример

### Requirement: Строковые обязательства и контрпримеры

Совместимость requires, пути if/else, внутренние вызовы и модульные ensures SHALL применять к string прежние правила. Слабые гарантии callee и лимиты solver SHALL сохранять unknown. Disproved SHALL содержать полный точный вход. Если строковую модель нельзя материализовать в пределах лимита декодирования, результат SHALL быть unknown без усечённого контрпримера.

#### Scenario: Противоречивая строка
- **WHEN** requires требует s === "" && s !== ""
- **THEN** результат inconsistent и доказательство реализации отсутствует

#### Scenario: Guard вызова
- **WHEN** callee требует s !== "", а caller вызывает его только после исключения пустой строки
- **THEN** предусловие вызова доказано; без guard найден конкретный пустой вход

#### Scenario: Неиспользуемая строка
- **WHEN** числовое нарушение найдено в функции с неиспользуемым string-параметром
- **THEN** полный вход содержит конкретную строку вместо incomplete-counterexample

### Requirement: Целочисленное деление

Верификатор SHALL моделировать bigint `/` с отбрасыванием дробной части результата при ненулевом делителе, сохраняя произвольную точность и знак без преобразования в number. Деление SHALL поддерживаться во всех проверяемых числовых выражениях с прежними правилами модульных контрактов и лимитов solver.

#### Scenario: Знаки и неполное частное

- **WHEN** проверяются 7n / 3n, -7n / 3n, 7n / -3n, -7n / -3n и 1n / -3n
- **THEN** результаты равны 2n, -2n, -2n, 2n и 0n соответственно

#### Scenario: Большие значения и контрпримеры

- **WHEN** неверное постусловие нарушается на частном bigint за пределами safe integer
- **THEN** disproved сохраняет полный точный вход, воспроизводящий нарушение в JavaScript

#### Scenario: Недостаточный контракт или лимит

- **WHEN** проверка деления зависит от недостаточного callee-контракта или solver исчерпывает лимит
- **THEN** сохраняется unknown без выдуманного контрпримера или proved

### Requirement: Область определения bigint-деления

Перед доказательством условия верификатор SHALL исключить нулевые bigint-делители в его вычисляемых зависимостях с учётом requires, путей и короткого замыкания. Возможное деление на ноль SHALL давать unknown/unsupported-dependency без counterexample; неполученный ответ solver SHALL давать unknown/solver-unknown. Проверка SHALL NOT молча исключать входы с нулевым делителем.

#### Scenario: Защита деления

- **WHEN** requires исключает y === 0n либо ветвь возвращает значение до x / y при y === 0n
- **THEN** деление проверяется на оставшихся путях

#### Scenario: Короткое замыкание

- **WHEN** requires содержит y !== 0n && x / y > 0n или y === 0n || x / y > 0n
- **THEN** невыполняемое деление при y === 0n не препятствует проверке

#### Scenario: Небезопасный предикат

- **WHEN** requires вычисляет x / y до проверки y !== 0n
- **THEN** совместимость и зависящие обязательства имеют unknown вместо использования значения деления на ноль

#### Scenario: Небезопасная зависимость

- **WHEN** тело, ensures, условие пути или вычисляемый аргумент в зависимости обязательства допускает деление на 0n
- **THEN** затронутое обязательство имеет unknown, даже если его формула без проверки деления была бы тождественной

#### Scenario: Гарантия не оправдывает собственное деление

- **WHEN** ensures callee содержит потенциальное деление на ноль
- **THEN** эта гарантия не используется для устранения нулевого делителя при проверке собственной области определения

#### Scenario: Выборочная область проверки

- **WHEN** деление находится вне зависимостей заданных условий и вызовов
- **THEN** сохраняется прежняя выборочная область проверки; отчёт не обещает отсутствие исключений во всём теле функции

# source-analysis Specification


## Purpose

Определить поддерживаемый язык TypeScript, привязку контрактов к исходным функциям и проверяемые свойства промежуточного представления при переносе существующего анализатора.

## Requirements

### Requirement: Проверка типов входной программы

Анализатор SHALL проверять входной файл и его зависимости с настройками strict, noImplicitReturns, ES2022 и NodeNext до построения проверяемой программы. Эти настройки SHALL применяться независимо от пользовательского tsconfig.json. Ошибки типов SHALL прерывать анализ с причиной type-error.

#### Scenario: Ошибка типов в импортированной реализации

- **WHEN** достижимая импортированная функция объявляет bigint-результат, но возвращает строку
- **THEN** анализ завершается ошибкой type-error и доказательства не выполняются

#### Scenario: Подавление диагностики

- **WHEN** достижимый исходный модуль содержит директиву @ts-ignore, @ts-nocheck или @ts-expect-error
- **THEN** анализатор отклоняет модуль, даже если TypeScript не сообщил ошибку типов

### Requirement: Явный граф локальных модулей

Анализатор SHALL включать входной .ts-файл и runtime-модули, достижимые через относительные value imports и re-exports, включая side-effect imports. Type-only зависимости SHALL проверяться TypeScript без добавления реализаций в runtime-граф. API src/contract.ts и API этого экземпляра пакета (import из ts-value-proof) SHALL распознаваться по модулю и символу. Неимпортированные файлы SHALL NOT автоматически включаться в проверяемый граф.

#### Scenario: Контракт в отдельном модуле

- **WHEN** входной файл импортирует реализацию и подключает модуль её контракта через side-effect import
- **THEN** анализатор связывает контракт с импортированной функцией и включает её реализацию в проверку

#### Scenario: Ошибочная функция вне графа

- **WHEN** соседний .ts-файл не достижим из входного файла
- **THEN** его функции не добавляются в проверяемый граф

#### Scenario: Установленный API

- **WHEN** исходник импортирует contract из установленного ts-value-proof, в том числе через переименование или barrel
- **THEN** анализатор распознаёт доверенный API; другой модуль с одноимённой функцией доверенным не становится

### Requirement: Поддерживаемые формы модулей

Анализатор SHALL поддерживать относительные named value imports, named/star re-exports, локальные named exports, type/interface declarations и относительные type-only imports/exports. Type-only зависимости SHALL проверяться TypeScript без исполнения. Default/namespace value imports, сторонние runtime-пакеты кроме доверенного API ts-value-proof, import attributes, runtime-циклы, .d.ts вместо реализации кроме доверенного API и произвольный исполняемый top-level код SHALL отклоняться.

#### Scenario: Цепочка re-exports

- **WHEN** вызов разрешается через named re-export и export * до поддерживаемой функции
- **THEN** целью вызова остаётся исходное объявление этой функции

#### Scenario: Неподдерживаемый достижимый модуль

- **WHEN** граф содержит циклический импорт, declaration-only модуль вместо runtime-реализации, namespace import или top-level console.log
- **THEN** анализатор отклоняет программу

#### Scenario: Именованный непрозрачный тип

- **WHEN** параметр использует type/interface из локального .ts или .d.ts через import type
- **THEN** тип разрешается, но type-only модуль не исполняется и не считается реализацией

### Requirement: Идентичность функций и aliases

Анализатор SHALL разрешать функции по исходным TypeScript-символам, включая цепочки const aliases без аннотаций. Разные объявления с одинаковыми именами или сигнатурами SHALL сохранять независимую идентичность. Изменяемые, аннотированные и приведённые через type assertion aliases SHALL отклоняться.

#### Scenario: Несколько aliases одной функции

- **WHEN** контракт задан для const alias, а вызов использует другой alias той же функции
- **THEN** контракт и вызов связываются с одним исходным объявлением

#### Scenario: Совпадающие имена в разных модулях

- **WHEN** две импортированные функции имеют одинаковые имена и сигнатуры
- **THEN** их контракты и результаты проверки остаются раздельными

#### Scenario: Аннотированный alias

- **WHEN** alias объявлен с явным типом функции, через let или через type assertion
- **THEN** анализатор отклоняет alias

### Requirement: Распознавание объявления контракта

Анализатор SHALL принимать один вызов доверенного contract API на исходную функцию с двумя аргументами и без явных type arguments. Спецификация SHALL быть inline-объектом с requires, ensures или обоими в форме expression arrow functions. Пустой контракт, повторный контракт, отсутствие контрактов и одноимённый посторонний API SHALL отклоняться.

#### Scenario: Повторный контракт через alias

- **WHEN** контракт объявлен для функции и повторно для её alias или импортированного имени
- **THEN** анализатор сообщает о повторном контракте одного символа

#### Scenario: Сохранённая спецификация

- **WHEN** вторым аргументом contract передана переменная вместо inline-объекта
- **THEN** статический анализатор отклоняет такую форму независимо от совместимости её TypeScript-типа

#### Scenario: Посторонняя функция contract

- **WHEN** программа объявляет собственную функцию с именем contract
- **THEN** её вызов не принимается за объявление проверяемого контракта

#### Scenario: Один предикат

- **WHEN** inline-контракт содержит только requires либо только ensures
- **THEN** анализатор сохраняет ровно объявленный предикат

### Requirement: Привязка параметров предикатов

Анализатор SHALL связывать параметры requires с аргументами исходной функции по позиции и символам. Первый параметр ensures SHALL обозначать результат, остальные — исходные аргументы. Имена параметров предикатов могут отличаться; неиспользуемые завершающие параметры могут отсутствовать. Предикаты SHALL возвращать boolean.

#### Scenario: Переименованные параметры

- **WHEN** функция принимает balance и amount, а её предикаты используют b и a
- **THEN** условия проверяются относительно соответствующих аргументов исходной функции

#### Scenario: Предикат без параметров

- **WHEN** requires задан как () => true
- **THEN** анализатор принимает предикат без объявления неиспользуемых аргументов

#### Scenario: Неиспользуемый промежуточный параметр

- **WHEN** requires для (label: string, x: number) записан как (_label, x) => x >= 0
- **THEN** привязка x сохраняет вторую позицию; объявление _label не создаёт зависимости от строки

### Requirement: Сигнатуры проверяемых функций

Анализатор SHALL принимать именованные sync-функции с доступным телом, явными обязательными параметрами и явным результатом произвольных TypeScript-типов. Неподдерживаемые значения SHALL оставаться непрозрачными без числовой интерпретации. Generics, overloads, async/generator, неявный результат, optional/rest/default/this, деструктуризация и имена this, requires, ensures, output, BigInt, result SHALL отклоняться.

#### Scenario: Поддерживаемая функция

- **WHEN** функция объявлена как function identity(x: bigint): bigint с доступным телом
- **THEN** анализатор принимает её сигнатуру

#### Scenario: Расширенная сигнатура

- **WHEN** функция использует generic, overload, optional/rest/default/this-параметр или неявный тип результата
- **THEN** анализатор отклоняет сигнатуру

#### Scenario: Явная number-сигнатура

- **WHEN** функция объявлена как function identity(x: number): number с доступным телом
- **THEN** анализатор принимает сигнатуру; для условия, использующего результат функции без параметров, модель определяется типом результата

#### Scenario: Нечисловые аргументы не нужны условию

- **WHEN** функция принимает string, object, boolean, callback, union, any или unknown, а requires использует только отдельный number-параметр
- **THEN** сами типы сигнатуры не препятствуют проверке requires; обращения к непрозрачным значениям не получают числовую семантику

#### Scenario: Нечисловой результат

- **WHEN** requires-only функция возвращает неиспользуемый строковый параметр
- **THEN** проверка requires не требует числового результата

### Requirement: Числовая модель входного языка

Анализатор SHALL сохранять точность bigint-литералов различных оснований и с разделителями цифр без преобразования в number. Number-литералы SHALL сохранять значение JavaScript binary64, включая округление, переполнение и знак нуля. Смешанные числовые выражения в проверяемых зависимостях SHALL отклоняться; неявное преобразование между bigint и number SHALL NOT выполняться.

#### Scenario: Большой шестнадцатеричный литерал

- **WHEN** исходник содержит 0xffff_ffff_ffff_ffffn
- **THEN** IR хранит точную десятичную строку 18446744073709551615

#### Scenario: Функция над number

- **WHEN** проверяемое условие зависит от number-параметра или number-результата
- **THEN** анализатор выбирает точную модель binary64 без подмены на математические вещественные числа

#### Scenario: Округлённый и граничные литералы

- **WHEN** number-функция использует 9007199254740993, 5e-324, 1e309, -0 либо numeric literal другого основания с разделителями
- **THEN** значения совпадают с JavaScript: соответственно 9007199254740992, минимальное положительное subnormal, Infinity, отрицательный ноль и binary64-значение литерала

### Requirement: Поддерживаемые выражения и управление потоком

Анализатор SHALL поддерживать return, if/else, вложенные блоки, ранние возвраты и продолжения ветвей; +, -, *, /, унарный минус, сравнения, строгое равенство, boolean-литералы и &&, ||, !. Условия SHALL иметь тип boolean. Непрозрачные параметры и null-литералы SHALL допускаться в передаче и возврате вне зависимостей условия. Неподдерживаемая операция в зависимости SHALL давать unknown/unsupported-dependency. Локальные переменные, мутации, циклы, try/catch, исходный ?: и числовая truthiness SHALL оставаться структурно неподдерживаемыми.

#### Scenario: Вложенная неполная ветка

- **WHEN** тело содержит if (x > 0n) { if (x > 1n) return 2n; } return 0n
- **THEN** представление тела сохраняет возврат 2n для x > 1n и продолжение с 0n для остальных путей

#### Scenario: Неподдерживаемая операция

- **WHEN** тело использует остаток, возведение в степень, исходный тернарный оператор или неявную проверку истинности bigint
- **THEN** остаток или возведение в степень в зависимости дают unknown/unsupported-dependency; неподдерживаемая структура тернарного оператора или числовая truthiness отклоняется

#### Scenario: Number без расширения операторов

- **WHEN** number-функция использует %, **, bitwise, нестрогое равенство, Math API или числовое условие if
- **THEN** неподдерживаемая операция в зависимости получает unknown/unsupported-dependency; структурно неподдерживаемые вызовы Math API и числовое условие if отклоняются как unsupported-code после проверки типов

#### Scenario: Числовое умножение

- **WHEN** bigint- или number-выражение использует `*` в return, requires, ensures, условии ветви или аргументе внутреннего вызова
- **THEN** анализатор сохраняет типы, приоритет и вложенность операции без неявного преобразования операндов

#### Scenario: Числовое деление

- **WHEN** bigint- или number-выражение использует `/` в return, requires, ensures, условии if/switch или аргументе внутреннего вызова
- **THEN** анализатор сохраняет типы, приоритет и левую ассоциативность без неявного преобразования операндов

### Requirement: Ограничения вызовов

Анализатор SHALL разрешать вызовы поддерживаемых функций с контрактами внутри возвращаемых выражений. Он SHALL отклонять вызовы функций без контрактов, вызовы в условиях и предикатах, вложенные вызовы в аргументах и прямую или косвенную рекурсию.

#### Scenario: Несколько вызовов в результате

- **WHEN** return содержит сумму двух вызовов поддерживаемой функции с контрактом
- **THEN** оба исходных вызова включаются в проверку

#### Scenario: Неподдерживаемое место вызова

- **WHEN** вызов находится в условии if, предикате контракта или аргументе другого вызова
- **THEN** анализатор отклоняет программу

### Requirement: Проверка целостности IR

Публичная проверка IR SHALL отклонять неправильные типы выражений, свободные переменные, result вне ensures, пустой объявленный контракт, потерю указанного предиката или нужной зависимости, неправильные цели или аргументы вызовов, рекурсию, неверные позиции и нарушение покрытия исходных функций, контрактов или вызовов. Backend SHALL выполнять эту проверку до запросов к solver.

#### Scenario: Повреждённое представление

- **WHEN** переданное в backend IR содержит отсутствующую функцию, дробный bigint-литерал, неизвестную переменную или неправильное число аргументов
- **THEN** проверка завершается ошибкой Invalid IR до доказательства

#### Scenario: Потерянный недостижимый вызов

- **WHEN** преобразование удаляет исходный вызов после безусловного return
- **THEN** несовпадение покрытия вызовов приводит к отказу

#### Scenario: Повреждённый number IR

- **WHEN** IR содержит неправильное binary64-значение, разные числовые типы операндов, результата ветви или аргумента callee
- **THEN** проверка завершается Invalid IR до запросов к solver

#### Scenario: Потерянный аргумент после выборки

- **WHEN** представление удалило непрозрачный параметр из исходной арности или неправильно связало позицию числового аргумента
- **THEN** проверка целостности отклоняет представление до solver

### Requirement: Общие продолжения ветвей

Анализатор SHALL сохранять исходную идентичность вызова, когда продолжение копируется в несколько ветвей IR. Все копии одного вызова SHALL иметь согласованную форму, а набор исходных вызовов SHALL оставаться полным.

#### Scenario: Копии одного исходного вызова

- **WHEN** общий return с вызовом достижим через два пути после вложенных if
- **THEN** обе копии имеют один исходный call ID и сохраняют отдельные условия пути

#### Scenario: Несогласованная копия

- **WHEN** в IR одна копия вызова с тем же ID имеет изменённые аргументы
- **THEN** проверка целостности отклоняет конфликтующую идентичность вызова

### Requirement: Однородность числовой модели графа

Анализатор SHALL выбирать числовую модель по зависимостям проверяемых условий и вызовов. Неиспользуемые параметры и результаты SHALL NOT навязывать числовую модель. Если проверяемым зависимостям нужны обе модели, граф SHALL отклоняться с unsupported-numeric-model без частичного успешного отчёта; преобразования типов не добавляются.

#### Scenario: Несвязанные функции разных моделей

- **WHEN** достижимый модуль содержит отдельные bigint- и number-функции с проверяемыми условиями обеих моделей
- **THEN** весь граф получает отказ unsupported-numeric-model без частичного успешного отчёта

#### Scenario: Неиспользуемый bigint рядом с number

- **WHEN** функция принимает x: number и token: bigint, а заданное условие использует только x
- **THEN** token не препятствует number-проверке

### Requirement: Особые number-константы и идентичность символов

Анализатор SHALL принимать стандартные глобальные NaN и Infinity в number-выражениях и сохранять их значение. Он SHALL различать эти глобальные символы и одноимённые параметры по привязке символов. Произвольные свободные идентификаторы SHALL оставаться неподдерживаемыми.

#### Scenario: Глобальная бесконечность

- **WHEN** предикат number-контракта использует x < Infinity и x > -Infinity
- **THEN** обе границы обозначают соответствующие бесконечности

#### Scenario: Параметр с именем Infinity

- **WHEN** функция принимает number-параметр Infinity и возвращает его
- **THEN** анализатор связывает выражение с аргументом, а не с глобальной бесконечностью

### Requirement: Полнота зависимостей выборочной проверки

Анализатор SHALL учитывать зависимости предиката по данным, управлению потоком, фактическим аргументам и вызовам. Неподдерживаемая зависимость SHALL давать локальный unknown с исходной позицией. Исходные вызовы SHALL сохраняться независимо от использования результата; непроверенный код SHALL NOT считаться доказанным.

#### Scenario: Непрозрачный выбор результата

- **WHEN** ensures проверяет числовой результат, выбираемый условием if по boolean-параметру
- **THEN** implementation имеет unknown/unsupported-dependency, а независимый числовой requires остаётся проверяемым

#### Scenario: Внутренний вызов без нужного результата

- **WHEN** requires-only функция содержит вызов callee с requires
- **THEN** обязательство call сохраняется, хотя собственного ensures нет

#### Scenario: Эффект в неиспользуемом аргументе

- **WHEN** неиспользуемый аргумент вызова вычисляется через callback или getter
- **THEN** выражение не удаляется как безопасное; зависимость или структура получает явный отказ

### Requirement: Базовые строковые выражения

Анализатор SHALL поддерживать параметры и результаты типа string, строковые литералы, шаблоны без подстановок, string + string, ===, !== и .length примитивной строки. Длина SHALL иметь тип number. Строковые зависимости SHALL сочетаться с number, но не с bigint. Неиспользуемая строка SHALL NOT навязывать модель. Остальные строковые операции SHALL получать явный отказ без coercion.

#### Scenario: Строка и длина
- **WHEN** функция принимает строку и число, возвращает конкатенацию, а контракт сравнивает длину с числом
- **THEN** анализ сохраняет типы и все зависимости, включая .length в аргументе поддерживаемого вызова

#### Scenario: Неподдерживаемые операции
- **WHEN** программа использует s + 1, s < t, s[0], s.slice(1) либо шаблон с подстановкой
- **THEN** операция получает unsupported-dependency или структура отклоняется как unsupported-code; доказательство для неё не выдаётся

#### Scenario: Повреждённая строковая модель
- **WHEN** IR содержит нестроковый литерал string, .length числа или string + number как поддерживаемую операцию
- **THEN** проверка отклоняет IR до solver

### Requirement: Выбор и продолжение switch

Анализатор SHALL поддерживать switch с упорядоченными case и необязательным default в любой позиции. Выбор SHALL использовать строгое равенство и первое совпадение; при отсутствии совпадений выполняется default или продолжение после switch. Пустые метки и завершение ветви без return/break SHALL сохранять fallthrough. Все пути SHALL возвращать значение согласно прежним ограничениям анализатора.

#### Scenario: Строгое сравнение
- **WHEN** switch выбирает между метками number, bigint или string в поддерживаемой однородной модели
- **THEN** результат совпадает с JavaScript, включая NaN, равенство +0/-0, большие bigint и точные UTF-16 строки

#### Scenario: Default посередине
- **WHEN** default расположен перед совпавшим case
- **THEN** выполнение начинается с совпавшего case; при отсутствии совпадений начинается с default и сохраняет дальнейший fallthrough

#### Scenario: Пустые и повторные метки
- **WHEN** несколько case имеют общее тело или одинаковое значение
- **THEN** выбор начинается с первой совпавшей метки и проходит следующие тела без повторного выбора

#### Scenario: Продолжение после switch
- **WHEN** switch пуст, не имеет совпадения без default или последняя ветвь завершается без return
- **THEN** выполняется код после switch; отсутствие необходимого возврата отклоняется

### Requirement: Выход из switch

Анализатор SHALL поддерживать break без метки внутри switch, в том числе внутри if и блоков, и вложенные switch. Break SHALL переходить к продолжению после ближайшего switch, а return SHALL завершать функцию. Метки и break с меткой SHALL оставаться неподдерживаемыми.

#### Scenario: Условный break
- **WHEN** внутри case выполняется if с break на одном пути и return либо fallthrough на другом
- **THEN** только путь break переходит к коду после switch

#### Scenario: Вложенный switch
- **WHEN** break завершает внутренний switch
- **THEN** выполнение продолжается внутри внешнего case, а внешний break завершает внешний switch

### Requirement: Ограничения и покрытие switch

Выражение выбора и метки SHALL исключать вызовы, мутации и потенциальные getters. Неподдерживаемые операции и непрозрачные значения в проверяемых зависимостях SHALL сохранять unknown/unsupported-dependency. Ограничения числовых моделей SHALL сохраняться. Копии исходных вызовов при преобразовании switch SHALL сохранять call ID, аргументы, позиции и условия пути; потеря исходного вызова SHALL приводить к отказу.

#### Scenario: Недопустимое вычисление выбора
- **WHEN** выражение switch либо case содержит вызов, присваивание, инкремент или доступ к свойству кроме length примитивной строки
- **THEN** анализ отклоняет структуру как unsupported-code после проверки типов, даже в пустом switch

#### Scenario: Неподдерживаемая зависимость
- **WHEN** выбор проверяемого результата зависит от остатка или непрозрачного boolean-параметра
- **THEN** затронутое обязательство получает unknown/unsupported-dependency, а независимые условия остаются проверяемыми

#### Scenario: Общий вызов
- **WHEN** return с вызовом достигается через fallthrough и прямой выбор case либо через общий код после break
- **THEN** все копии сохраняют одну исходную идентичность и проверяются при соответствующих условиях пути

#### Scenario: Недостижимый исходный вызов
- **WHEN** преобразование теряет вызов после безусловного break или return
- **THEN** анализатор отклоняет программу из-за нарушения покрытия вызовов

# Design

## Context

`prepareSource` создаёт типизированный `ProgramIR`. В `scripts/verification-engine.ts` обход путей, подстановка параметров, построение выражений Z3 и запуск solver сегодня связаны внутри `verifyWithModel`. В `scripts/verifier.ts` общий статус вычисляется из локальных результатов. CLI и Vite используют это ядро. Регрессионные тесты уже опираются на воспроизведение конкретной модели Z3.

## Goals / Non-Goals

Сравнение начинается на границе общего IR. Ошибка в разборе TypeScript или понижении обеих ветвей до общего IR может затронуть оба доказательства. Формальная верификация адаптера и моделирование binary64, UTF-16, умножения, деления и абстрактных результатов callee в Lean выходят за рамки первой версии.

## Decisions

1. **Один снимок и явный перечень обязательств.** Выделить идентичность обязательства до построения выражений решателя. В ключ входят ID функции, вид проверки, позиция конкретного предиката и для вызова его callId и идентификатор экземпляра пути. Общими могут быть обход `callPaths` и структурные привязки к IR. Сопоставлять по напечатанному условию или индексу независимо отфильтрованных массивов нельзя: одинаковый callId уже встречается на нескольких путях. Проверять полноту и однозначность сопоставления.
2. **Два перевода.** Сохранить текущие операции и защитные проверки Z3. Lean получает типизированные выражения предпосылок, пути, аргументов и цели из того же IR, независимо отображает их в `Int`, логические связки и условные выражения. Для `ensures` подставлять выражение результата, а параметры связывать с исходными значениями. Для `call` использовать предусловия caller и фактические аргументы. Локальные связывания, sequence и тернарные узлы проверять с учётом вычисляемых зависимостей. Явно отклонять обязательство, если для его перевода пришлось бы отбросить зависимость. Печать SMT-LIB, разбор prettyExpr или передача модели Z3 лишили бы проверку независимости.
3. **Доказательство двух полярностей.** Для проверки контракта сформировать цель `∀ xs, assumptions xs → goal xs` и её отрицание, для совместимости — `∃ xs, requires xs` и её отрицание. Использовать ограниченную ресурсами автоматизацию линейной арифметики. Для существования допустимо внутри Lean подобрать целые и проверить подстановку ядром (также для отрицания универсальной цели). В частности, пара 0 и 1 должна обнаруживаться общей процедурой без специального правила для withdraw. Возвращать наружу только доказанную полярность. Неуспех тактики, тайм-аут или ошибка компиляции не служат доказательством противоположной полярности. Не передавать в Lean ответ, контрпример или направление, выбранное Z3.
4. **Запуск Lean.** Вызывать локально установленный совместимый Lean 4, зафиксировать проверенную версию в toolchain для интеграционных тестов и описать установку отдельно. Обычная проверка пытается использовать Lean автоматически, без загрузки toolchain из сети. Передавать только сгенерированные типизированные конструкции со своими именами переменных. Допускать только проверенные ядром результаты без `sorry`, новых аксиом и непроверяемых вычислительных оракулов. Использовать раздельные бюджеты для доказательств, ограничить время процесса и освободить его и временные файлы после завершения или ошибки. Поддержать повторные и одновременные вызовы без смешения результатов. Отсутствие или несовместимость бинарника даёт unavailable; неудачная попытка доказательства, сбой процесса или некорректный ответ дают unknown с причиной.
5. **Слияние результатов.** Сначала сопоставить совместимость предусловий. При её конфликте подавить успешные зависимые выводы и объяснить причину. Для остальных строк сравнивать определённые вердикты только внутри одного ключа. Вложенная запись сохраняет оба исходных статуса, существующее поле status становится локальным итогом. Не переносить модель в публичный counterexample при конфликте. Суммировать итоговые строки по прежнему приоритету inconsistent, refuted, unknown, verified. Например, конфликт в одной строке и независимое бесспорное нарушение в другой дают общий refuted и видимую строку disagreement. Генератор использует итоговую строку и прежнее подтверждение исполнением. При ошибке подготовки без IR сохраняется обычный диагностический отчёт с пустым results.

## Risks / Trade-offs

- Общий IR ограничивает независимость. Проверять условие и его отрицание на малых известных примерах и включить случаи с подстановкой, ранним выходом и общей точкой вызова на разных путях.
- Lean может доказать меньше условий в заданное время. Различать недоступный инструмент, неподдерживаемую семантику и отсутствие доказательства. Интеграционные тесты с реальным Lean должны требовать agreed на согласованном минимальном наборе.
- Процесс Lean добавляет задержку. Группировать обязательства одного снимка при сохранении индивидуальных вердиктов и лимитов. Основной путь npm и пакет runtime не должны устанавливать Lean или загружать его при импорте контракта.

## Migration Plan

Расширить общий тип отчёта и опубликованные declarations аддитивными полями. Обновить русскую и английскую документацию примерами agreed, unconfirmed и disagreement, включая поведение без Lean. До выпуска проверить обычный CLI, установленный пакет, Vite и генератор регрессий. Для отката удалить подключение сравнения в общем ядре и вернуться к существующему пути Z3.
